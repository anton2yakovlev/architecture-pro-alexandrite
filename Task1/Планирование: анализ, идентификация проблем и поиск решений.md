# Существующие и потенциальные проблемные места

- Задержка заказов пользователей
- Отсутствие мониторингов и алертов. Нет возможности понять что проблема вообще возникла
- Неудобный интерфейс для операторов
- Нет автоматического CI/CD в release и prod контуре
- Сложная интеграция статосов заказа между тремя системами
- Отсутствие автотестов
- Задержки на стороне команды разработки при выпуске нового функционала и починке багов
- Существует узкое место для обработки 3D моделей
- Мощности производства позволяют масштабировать бизнес, но IT система не позволяет выдержать такую нагрузку
- Отсутствие реплик БД и горизонтального масштабирования приложения

# Инициативы для устранения проблемных мест

- Повышение observability проекта. Все компонтенты должны быть обложены мониторингами, логированием и алертами. Нужно понять по какой причине происходят проблемы с заказами.
    - Сбор метрик через Prometheus
    - Визуализация в Grafana
    - Добавление Jaeger для трейсинга
    - Добавление ELK стека
- Глубокий анализ MES. Операторы выполняют ключевую роль в выполнении заказов и у них не должно быть сложностей с этим. Надо понять почему приложение тормозит и принять меры.
    - Добавление кэширования для MES. Одно из возможных решений, но принимать его надо только после анализа
    - Автоматическое распределение заказов на операторов. Можно придумать алгоритмы на основе происходительности оператора, тогда награда не будет зависеть от удачи.
    - Мастабирование системы. Если окажется что проблемы с производительностью из-за нехватки мощностей, то стоит масштабировать приложение чтобы выдерживать нагрузку.
- Настройка пайпланов для быстрого релиза (и отката) для всех окружений. Это повысит time-2-market и удобство тестирования.
- Создание автотестов. Если для этого не хватает ресурсов, то нанять автотестировщика или сделать это через аутсорс. Это позволит быстрее выпускать фичи и простимулирует более надежное планирование спринтов.
- Неправильная оценка сроков в спринтах может свидетельсвовать либо о плохом менеджменте, либо о нехватке ресурсов, либо о неполном представлении команды о всех проблемах. Нужно провести ретроспективные встречи по предыдущим багам и задачам, чтобы понять истиную причину задержек и неправильных сроков. Необходимо найти первопричину.
- `Скорость расчёта стоимости зависит от количества полигонов в 3D-модели`. Нужно изучить возможность масштабирования компоненты, которая занимается обработкой 3D. Долгое время ожидания пользователем может вытекать в отказ клиентов от услуги.
- Масштабирование системы. Сейчас продукт может работать ненадежно, плюс никто не знает реальных причин задержки заказов, возможно система просто не справляется с нагрузкой. Необходимо детально изучить мониторинги (после их добавления) и начать с тех кусков, которые вызывают проблемы.

# Приоритет инициатив

На данный момент отсутствует хорошая наблюдаемость за проектом. Это не позволяет даже выявить причины проблем в продукте. Соответственно первыми шагами будет сбор данных и аналитика, а только после этого можно будет эффективно расставить приоритеты.

Три важнейшие инициативы, с которых стоит начать:
1) **Повышение observability проекта.** Таким образом мы определим почему заказы зависают и пользователи остаются недовольны. На этом же этапе стоит добавить ключевые бизнес-метрики, такие как среднее время выполнение заказа и каждого этапа.
2) **Ретроспективные встречи команды.** Разбор конкретных ситуация почему команда не уложилась в спринт и почему баги фиксятся так долго. Результатом каждой встречи должны быть ясные action points.
3) **Масштабирование системы.** Уже сейчас очевидны проблемы с происховодительностью. Нужно добавить репликацию БД и сделать настроить авторепликацию основного приложения на spring.

Все эти действия позволят понять реальное положение дел. После этого нужно будет заново переоценить все остальные инициативы с учетом новой информации.
