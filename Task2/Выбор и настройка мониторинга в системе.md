# Выбор и настройка мониторинга в системе

Яндекс Метрика даёт картину только по сайту. Заказы через API, расчёт стоимости в MES и обмен статусами через RabbitMQ для неё невидимы. Чтобы понимать, где заказы застревают и почему партнёры не получают ответы, нужна наблюдаемость внутри системы. Без этого улучшения будут неполными, а бизнес продолжит терять контракты и клиентов.

---

## Мотивация

1. **Прозрачность цепочки заказа.** Сейчас нельзя ответить на вопрос "где заказ": после SUBMITTED он уходит в MES по API или через очередь. Нужны метрики по переходам статусов и задержкам между ними, чтобы находить узкие места (расчёт цены, очередь, CRM/MES).

2. **Контроль API и партнёров.** Заказы от других продавцов идут через MES API. Жалобы "не получили заказ" часто связаны с таймаутами, 5xx или долгим расчётом. Нужны RPS, латентность и ошибки по API и по источнику (B2C/партнёр).

3. **Очереди RabbitMQ.** CRM и MES обмениваются сообщениями через RabbitMQ. Рост глубины очереди это прямой признак того, что заказы не доходят или обрабатываются с задержкой. Без метрик очередей мы реагируем постфактум уже после жалобы пользователей.

4. **Ресурсы и насыщение.** Один инстанс на каждое приложение и БД. При росте нагрузки нужно заранее видеть рост CPU, памяти, соединений к БД и объёма данных, чтобы планировать масштабирование до сбоев.

5. **Обоснование для бизнеса.** Потеря контрактов и репутации уже стоит дороже, чем внедрение мониторинга. Метрики дают факты для отчётов и приоритизации: что чинить в первую очередь (расчёт цены, очередь, конкретный API).

---

## Выбор подхода к мониторингу

- **Четыре золотых сигнала** - для всех трёх API (приложение на spring, CRM, MES): запросы, задержки, ошибки и утилизация ресурсов. Это стандартный способ видеть здоровье API и готовность к масштабированию.

- **USE** - для инфраструктуры: RabbitMQ (очереди, DLX, сообщения в полёте), БД (память, соединения, размер), приложения (CPU, память), S3 (размер хранилища). USE отвечает на вопрос "не исчерпали ли мы ресурс".

## Метрики по частям системы

### API (Shop, CRM, MES) - четыре золотых сигнала

| Метрика | Зачем | Ярлыки |
|--------|--------|--------|
| RPS (число запросов в секунду) для Shop / CRM / MES API | Нагрузка, планирование масштабирования, корреляция с ошибками. | `service` (spring app/crm/mes), `env`, `endpoint`, `http_method` |
| RPS per user для Spring app / CRM / MES API | Выявление аномально активных пользователей или партнёров, злоупотребления, квоты. | `service`, `user_id` или `partner_id` (для MES), `env` |
| Response time (latency) для Spring app / CRM / MES API | Качество ответа, деградации, регрессии после релизов. Важно для медленной первой страницы MES. | `service`, `endpoint`, `http_method`, `status_code` |
| Number of HTTP 200 / HTTP 500 для Spring app / CRM / MES API | Доля успешных и ошибочных ответов, SLO по ошибкам. | `service`, `endpoint`, `status_code` |
| CPU % и Memory utilisation для Spring app / CRM / MES API | Насыщение, когда пора масштабировать или оптимизировать. | `service`, `instance_id`, `env` |
| Number of simultaneous sessions для Spring app / CRM / MES API | Оценка реальной нагрузки по пользователям/партнёрам. | `service`, `env` |
| Kb transferred (received) / Kb provided (sent) для Spring app / CRM / MES API | Работа с 3D-моделями и большими файлами; контроль трафика и аномалий. | `service`, `endpoint`, при необходимости `partner_id` |

### RabbitMQ - USE

| Метрика | Зачем | Ярлыки |
|--------|--------|--------|
| Number of messages in flight в RabbitMQ | Сколько сообщений в обработке. Рост - беклог, задержка в смене статусов заказа. | `queue`, `routing_key`, `exchange` |
| Number of dead-letter-exchange letters в RabbitMQ | Отказы обработки, потерянные события. Нужно держать близко к нулю и расследовать при появлении. | `queue`, `reason`, при необходимости тип сообщения |

### Базы данных и хранилище - USE

| Метрика | Зачем | Ярлыки |
|--------|--------|--------|
| Memory utilisation для Spring app DB и MES DB | Риск OOM и падения БД. | `db` (Spring app/mes), `instance_id` |
| Number of connections для Spring app DB и MES DB | Исчерпание пула соединений, планирование пула/реплик. | `db`, `instance_id` |
| Size of Spring app DB/MES DB | Рост данных, планирование архивирования и бэкапов. | `db`, `instance_id` |
| Size of S3 storage | Хранение 3D-моделей; стоимость и лимиты. | `bucket`, при необходимости `storage_class` |

### Дополнительные метрики (не из списка)

- **Время перехода между статусами заказа** (например, SUBMITTED -> PRICE_CALCULATED -> MANUFACTURING_APPROVED -> … -> CLOSED). Позволяет находить узкие места в процессе и формулировать SLA для клиентов. Ярлыки: `channel` (web/partner), при необходимости `partner_id`.
- **Количество расчётов стоимости в MES в единицу времени и их длительность (p50/p95/p99).** Прямо связано с жалобами на «долго считает» и с партнёрским API. Ярлыки: `source` (b2c/b2b), `partner_id` при наличии.

## План действий

1. **Сбор метрик приложений и инфраструктуры.** Поднять Prometheus (или managed-аналог в Yandex Cloud). Добавить экспорт метрик: из Spring Boot (Shop API, CRM API) и из MES (C#) в формате Prometheus, плюс node_exporter на хостах. Подключить rabbitmq_exporter и postgres_exporter для БД. Цель - один источник правды по метрикам.

2. **Дашборды.** Grafana: отдельные панели по каждому API (RPS, latency, 5xx, CPU, память), по RabbitMQ (глубина очередей, in flight, DLX), по БД (соединения, память, размер). Сводный вид по «здоровью» системы.

3. **Сквозной идентификатор запроса.** Ввести trace_id/request_id в HTTP и прокидывать в RabbitMQ (заголовки). Нужно для связи логов и метрик с конкретным заказом и запросом.

4. **События смены статусов заказа.** Фиксировать переходы статусов (аудит-таблица или события в очередь) с временными метками. На основе этого считать метрики «время перехода» и строить дашборд по цепочке заказа.

5. **Алертинг.** Настроить алерты на: рост 5xx по API, рост глубины очередей и DLX в RabbitMQ, высокий CPU/память приложений и БД, рост числа соединений к БД. Канал оповещения - Slack/Telegram/почта по договорённости с командой.

6. **S3 и размеры БД.** Регулярный сбор размера S3 и объёма БД (через экспортеры или скрипты в Prometheus). Отдельная панель или метрики для планирования затрат и архивирования.

## Показатели насыщенности и действия при превышении

| Объект | Порог (предупреждение / критический) | Действие при превышении |
|--------|--------------------------------------|--------------------------|
| API: p95 latency | &gt; 500 ms (5 мин) / &gt; 1.5 s (5 мин) | Предупреждение в канал; при критическом - тикет, проверка регрессии и нагрузки. |
| API: доля 5xx | &gt; 1% (10 мин) / &gt; 5% | Тикет, разбор логов и метрик; при критическом - эскалация, возможно откат или отключение проблемного контура. |
| API: CPU | &gt; 75% (15 мин) / &gt; 90% (10 мин) | Предупреждение; при критическом - тикет на масштабирование (добавить инстанс) или оптимизацию. |
| RabbitMQ: сообщения в полёте / глубина очереди | Стабильный рост 3 окна подряд / рост выше порога (например, &gt; N) | Тикет на разбор потребителей и очередей; при критическом - рассмотреть временное увеличение воркеров. |
| RabbitMQ: DLX | &gt; 0.1% от потока / &gt; 1% | Тикет на разбор причин; при критическом - инцидент, возможно ограничение приёма по проблемному routing_key. |
| MES: время расчёта стоимости p95 | &gt; 15 мин / &gt; 30 мин | Тикет на оптимизацию и приоритизацию; при критическом - деградационный режим (например, приоритет для B2B-партнёров). |
| БД: число соединений | &gt; 80% от лимита / &gt; 95% | Тикет на настройку пулов и лимитов, подготовка к реплике; при критическом - временный rate-limit тяжёлых запросов. |
| БД / S3: размер | По плановым порогам (например, 80% от лимита) | Тикет на архивирование, очистку, увеличение квоты. |

Конкретные числовые пороги (N, проценты) можно уточнить после первых недель сбора метрик и согласовать с бизнесом как SLO.
